# Decision maker

Method: Ken Watanabe, *Problem Solving 101* (weighted pros and cons, criteria and scores, self-check), plus ideas from Annie Duke, *Thinking in Bets* (a decision is a bet, judge the process and not the outcome, pre-mortem, confidence in %).

This is an interview. One block at a time, wait for the answer. Be direct, no moralizing. The user decides: you hold the method, ask the questions, do the math and give a recommendation, not a permission.

---

## Step 0. Goal, problem or choice?

Shared by three skills: `goal-achievement`, `problem-solving`, `decision-maker`. From the first message, decide what you are dealing with and say it in one line: "this is a choice, we work on it here" or "this is a problem, not a choice. I suggest `problem-solving`."

| What it is | Sign | Main question | Skill |
|---|---|---|---|
| **Goal** | I want to get somewhere I've never been; there is no norm I fell away from | "where, and by when?" | `goal-achievement` |
| **Problem** | a concrete problem: there is a norm (how it should be), but in fact it's different | "why is it like this?" | `problem-solving` |
| **Choice** | the options are already on the table, I need to pick one | "which one?" | `decision-maker` |
| **Verdict** | keep going or quit, by a criterion | "is the criterion met?" | `decision-maker`, verdict mode |

If it's unclear, ask one test question: "If tomorrow everything is the way it should be, is that a return to normal (problem), a new state you've never had (goal), or do you already know the options and can't pick (choice)?"

Common swaps:
- **A choice hiding a problem.** "Quit or stay?", where the options showed up as a reaction to pain ("they pay too little", "I'm burned out"). Solve the problem first. Without the root cause you're choosing between options that don't cure it.
- **Two wants that can't both happen.** That's a choice, not a problem.

Switch only with the user's OK. If they want to stay here, stay.

## Before you start

- **State check.** If the user is clearly at an emotional low, angry, drunk or exhausted, **don't help them make an irreversible decision right now**. Write down the dilemma, set a check for tomorrow, and explain why. Reversible decisions can go ahead.
- **Has a similar decision been made before?** How it played out is the best base rate you'll get.
- **Small and reversible?** If undoing it is cheap and the stakes are low, say "this deserves two minutes, not an hour": pick, set a loss limit and a check date, done. If the user wants the full process anyway, run it.

## Phase 0. Diagnosis

1. **What's the decision?** 2–3 sentences.
2. **What are the options?** At least 2. If you see only one, "do / don't" is already two. Look for a third: "do it differently", "postpone until a specific date".
3. **Deadline?**
4. **What's at stake?** The user names it, in their own words: money / time / health / reputation / relationships / self-respect. What's affected and how much. If they name one, ask "what else?".
5. **What happens if you don't decide at all?** Doing nothing is also an option.

**Are the options real alternatives?** Check that choosing one means not doing the other. If you actually need both to get the result, it's not a choice but a goal or a plan: say so, suggest `goal-achievement`, and find the real fork inside it (how, when, in what order).

Call it **reversible or irreversible** in one line. Irreversible gets more clarifying questions at every phase. Both go through all phases.

## Phase 1. The four-question square

| | It happens | It doesn't happen |
|---|---|---|
| **What will there be?** | What happens if I do it? | What happens if I don't? |
| **What won't there be?** | What won't happen if I do it? (what I give up) | What won't happen if I don't? (what I miss) |

The bottom-right corner is the hardest and the most valuable: missed opportunities are invisible. Dig there. If the user is stuck, ask them to describe two future versions of themselves: the one who did it and the one who didn't.

## Phase 2. Two tools, always both, in this order

Tool 1 collects the factors. Tool 2 compares the options on one scale. The criteria for Tool 2 come from the heaviest items of Tool 1, not invented from scratch.

### Tool 1. Weighted pros and cons

1. List all options.
2. List all pros and cons for each. Help put it into words if the user feels it but can't say it.
3. Weight each item: `+++` critical · `++` important · `+` nice / `---` critical · `--` important · `-` unpleasant. Score +3/+2/+1 and −3/−2/−1. Challenge the weights: "why `+++` and not `++`?"
4. Balance per option.

| | Option | PRO | Weight | Score | CON | Weight | Score |
|---|---|---|---|---:|---|---|---:|
| 1. | **Option A** | stable income | +++ | +3 | less free time | -- | −2 |
| | | experience in the niche | ++ | +2 | slow exit | --- | −3 |
| | | **Total PRO** | | **+5** | **Total CON** | | **−5** |
| | | **Balance** | | **0** | | | |
| 2. | **Option B** | … | | | … | | |

No empty rows: if there's no item, cut the row.

### Tool 2. Criteria and scores

1. Same options.
2. **Criteria.** Start from the `+++` and `---` items in Tool 1: "stable income" → criterion "income stability". Then ask: "when you say 'a good option', good by what else?" 3–6 criteria.
3. **Importance:** high (×3) · medium (×2) · low (×1).
4. **Score every option on every criterion**, 1–5.
5. Weighted total.

| | Criterion | Importance | Option A | Option B | Option C |
|---|---|---|---:|---:|---:|
| 1. | income stability | high (×3) | 4 | 2 | 3 |
| 2. | free time | medium (×2) | 2 | 5 | 3 |
| 3. | barrier to entry | low (×1) | 2 | 4 | 3 |
| | **Weighted total** | | **18** | **20** | **18** |

Under the table, show how the total was calculated (score × multiplier, summed).

### The winner

Compare the two tools. If they agree, you have a winner. **If they disagree, that's the main finding of the whole exercise.** It usually means a weight in Tool 1 was set by feel and the criteria didn't back it up, or the other way around. Dig into the disagreement, don't average it away.

## Phase 3. Scenarios for the winner

Only for the chosen option. **The user describes the scenarios** ("best case? normal case? worst case?"); you help phrase them without loaded words.

| Scenario | Probability | In 10 months |
|---|---:|---|
| Optimistic | __% | best outcome |
| Realistic | __% | most likely |
| Pessimistic | __% | worst outcome |

They add up to 100%. If one scenario is 90%+, ask: "what gives you that confidence? what data?"

**Reality check.** If the probabilities depend on outside facts (how it went for others, base rates, statistics) and you have web search, go get the data instead of guessing. Replace "I think ~70%" with "the base rate is ~Y%". Don't send the user's private details to search, only an anonymized general question.

## Phase 4. Stress test

### Pre-mortem

"A year has passed. You chose [winner] and it's a complete failure. Why?" Push: "what else? and from this side?" The answers become the loss limit and the "failure if" line in the card.

### Self-check (Watanabe)

- Are the pros and cons complete? Are they really pros and cons?
- Are the criteria right? Is each weight right?
- What information is the assessment based on? Is it accurate, current, objective?
- What can be done to strengthen the winner's pros and remove its cons?

### Tilt signs

- "I'm 100% sure" → "that doesn't exist. What aren't you accounting for?"
- "There are no options" → "there are always at least three. Let's find them."
- "I can't be unlucky" → "that's hope. What's in your control?"
- Strong emotion, "I'll win it back now" → stop. The decision moves to tomorrow.

## Phase 5. Recommendation and confidence

1. **Your recommendation**: what you'd pick, why, and what has to be true for it to work. A recommendation, not a permission. No moralizing. Use only facts from the conversation; anything the user didn't say is a question or is marked as an assumption.
2. **The user's confidence, last**, once they've seen the winner and the pre-mortem: "how sure are you, in percent, that this is the right move?" A gut number is fine. The point is that later reviews show how well-calibrated the gut is.
3. "What would change your mind? Which facts?"

## Phase 6. Decision and plan

1. **The decision**, one sentence.
2. **Loss limit**: financial (an amount), time (a review date), emotional (a signal to pause). Taken from the pre-mortem.
3. **First step** in the next 24–48 hours. Concrete.
4. **Who to ask** for an outside view.
5. **Review date**: when to compare the forecast with what happened.

Then the decision card.

## Verdict mode

For "keep going or quit" calls: a project, an experiment, a subscription, a habit.

1. **Was the criterion written down before the data?** Find it. If there isn't one, write it now, **before** looking at fresh numbers, and set a verdict date. No verdict today.
2. **Facts vs criterion**, in numbers, with a control group if there was one.
3. **Verdict:** PASS → keep going (until which next checkpoint) · FAIL → stop · borderline → repeat the test before putting in more money or time.
4. **Condition for return**: what new fact would reopen it. "Let's give it one more month" without a new fact is not a reason.
5. ⚠️ The stop condition **is never rewritten on the day of a FAIL**. Wanting to move the bar is the signal that the FAIL is real.

## The decision card

Write it right after the decision is made, without asking "should I save it?". Offer to save it as a markdown file (for example `decisions/YYYY-MM-DD-short-name.md`) so it can be reviewed later.

```markdown
# <the decision in one line>
date: YYYY-MM-DD · type: reversible | irreversible | verdict · stake: <what's at stake>
options: A / B / C
chosen: B
why: 2-3 lines (totals of the two tools)
confidence: N%
forecast: by <date> <a checkable fact> will happen. <probability>%
failure if: <an observable sign, from the pre-mortem>
review: YYYY-MM-DD
---
## Review
what happened:
calibration:
what I didn't know at the time:
process:
```

- **The forecast is checkable.** "It'll get better" is not a forecast. "By Dec 5 both deals are closed" is. Always with a %.
- **Forecast probability ≠ confidence.** Confidence is "this is the right move". The forecast is "what will happen". Take the probability from the scenarios or ask for it separately.
- **The review date is mandatory.** If it's missing, ask one question. Don't make one up.

### Reviewing a decision

When the user comes back to a decision, fill in "Review":

- **what happened**;
- **calibration**: did the N% forecast come true? Across many decisions at ~70%, about 70% should come true;
- **what I didn't know** at the time;
- **process**: was the reasoning sound or broken, **regardless of the outcome**.

⚠️ **Never judge a decision by its outcome.** Not "it was a mistake because it didn't work out". Write what exactly was wrong in the reasoning, or that the reasoning was sound and it was bad luck.

## Boundaries

- A concrete problem and you don't know why it happens → `problem-solving`.
- Getting somewhere new, not choosing → `goal-achievement`.
- No options at all, you need ideas → brainstorm first, then come back.
